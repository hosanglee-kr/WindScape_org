2. 모드/우선순위 관점 점검

실제 사용자 입장에서는 대략 이런 모드들이 있어요:

OFF

프로필 실행 (user profile 기반)

스케줄 실행 (시간 기반 자동 동작)

Override (fixed/preset) – 잠시 강풍/특정 스타일로 덮어쓰기

Simulation – 실기 대신 sim 데이터만 돌리는 모드


지금 Web API 기준으로 보면:

프로필 시작: /api/control/profile/select

프로필 정지: /api/control/profile/stop

오버라이드: /api/control/override/fixed|preset|clear

FactoryReset, ConfigInit, Reload 등은 메타


🔍 체크 포인트

1. 우선순위 규칙이 명확한가?

CT10 내부에서 이미 어느 정도 정의했겠지만,
최소한 개념적으로 아래처럼 정리가 되어 있어야 합니다:

1. Override가 켜져 있으면 → 무조건 최우선


2. 그 다음은 유저가 직접 START한 프로필


3. 그 다음이 스케줄에 의한 자동 동작


4. 아무것도 없으면 → OFF 혹은 “기본 자연풍”



👉 이 우선순위가 코드로 명확하게 캡슐화되어 있는지 한 번 확인해 보시는 게 좋습니다.

예: CT10_ControlManager::resolveActiveSource() 같이 한 함수에서만 결정하도록.



2. 모드 전환 시 “서서히” 바뀌는지

예를 들어:

스케줄로 30% → 60% 로 변할 때

Override로 20% → 80% 로 확 튀길 때


PWM을 바로 바꾸면 모터/소음/사용자 체감 모두 거칠게 느껴질 수 있어요.

👉 S20_WindSolver / CT10 에서

목표 풍량과 현재 풍량 사이에 **soft ramp (예: 초당 5% 이내 변화)**를 두는 로직이 있는지

없다면 1차 저역통과 필터나 easing 함수 등을 추가하는 걸 권장합니다.

3. 풍량/소음/안전 관련 보완 아이디어

3-1. 팬 모델/특성 반영

지금은 PWM %만 전달되지만, 실제 각 선풍기에는:

시동이 안 거는 구간 (예: 0~15%는 모터 정지)

소음이 심해지는 구간

“가장 효율적인 체감 바람 구간” 등이 있어요.


👉 보완 아이디어:

1. system 또는 별도의 fanProfile 섹션에:

"fanModel": {
  "minStartPercent": 18,
  "minComfortPercent": 22,
  "maxComfortPercent": 65,
  "hardMaxPercent": 90
}


2. P10_PWM 쪽에서:

요청 duty를 직접 쓰지 말고,
위 설정에 맞춰 클리핑/매핑해서 실제 PWM으로 보내기

예: 090% 구간으로 스케일링




이렇게 하면 프리셋/스케줄/오버라이드 모두가 팬 특성에 자동 보정됩니다.


---

3-2. 과도 운전 / 발열 보호

하드웨어 센서가 아직 없다면 소프트하게라도:

특정 duty 이상 (예: >80%) 를 장시간(예: 2시간 이상) 유지하면

자동으로 60% 정도로 세이프티 다운

로그에 [CT10] Safety throttle applied 같은 것 남기기



이건 실제 고장 보호라기보단,

사용자가 깜빡 잊고 강풍 그대로 놔두는 상황을 방지하는 용도라
큰 리스크 없이 추가할 수 있습니다.

4. 모션 센서 & AutoOff 연계 점검

현재 구조

/api/motion/pir/feed → motion->feedPIR(bool)

/api/motion/ble/feed → motion->feedBLE(bool)

system.motion / motion config 에 PIR/BLE 사용 여부, 타임아웃 등 정의되어 있을 가능성


🔍 체크 포인트

1. PIR/BLE 조합 로직

OR / AND 조합, 우선순위 등

예: BLE 신호가 약해도 PIR이 자주 뜨면 “사람 있음”으로 보는지?



2. AutoOff / IdleTime 과의 연계

autoOff_en, autoOff_min 가 NVS에 있죠.

실제로는,

“모션 없음” 상태가 autoOff_min 이상 지속되면 → OFF

모션 다시 발생하면:

바로 이전 모드를 복귀할지?

아니면 스케줄/프로필에 다시 위임할지?




👉 여기 규칙을 명확히 하지 않으면,

“밤에 켜놓고 나갔는데 꺼지지 않는다”

“잠시 자리를 비웠는데 프로필이 날아가고 기본 바람으로 복귀한다” 같이
애매한 동작이 나올 수 있습니다.




제안: 명시적인 상태 머신 추가

CT10 내부에 (이미 비슷한 게 있을 것으로 보이지만) 논리상으로:

IDLE        : 팬 정지
ACTIVE      : 스케줄 or 프로필 or 수동 컨트롤로 동작
IDLE_WAIT   : 마지막 모션 이후 타임아웃 카운트 중
SLEEP       : AutoOff / 야간모드 등으로 완전 정지

모션 발생 시:

SLEEP → ACTIVE (설정값에 따라)


모션/시간 없음:

ACTIVE → IDLE_WAIT → SLEEP



이렇게 “모션 때문에 꺼졌다/켰다” 라는 사건이 분명하게 남게 만들면,
Debug 로그와 사용자 체감이 훨씬 일관됩니다.

5. 전원/리부트 상황에서의 동작

현재 요소

N10_NvsManager 가 run_mode / src / sched_no / uprofile_no / ovr_* 등 저장

SC10_init() 에서

Config load + NVS init → CT10 begin → WebAPI begin



체크 포인트

1. 전원 복구 시 “마지막 상태를 그대로 살릴지” 여부

예를 들어:

사용자가 밤에 강풍 프로필을 켜둔 상태에서
정전 → 재투입 되면,

다시 강풍으로 시작하는 게 맞나요?

아니면 “기본 OFF” / “스케줄에 의한 자동 켜짐만 허용”이 나을까요?




2. 권장 전략

Config에 하나 추가:

"system": {
  "powerOnBehavior": "OFF" | "LAST" | "SCHEDULE_ONLY"
}

그리고 CT10 초기화 시:

OFF → 무조건 정지

LAST → NVS에 저장된 run_mode 복원

SCHEDULE_ONLY →
“리부트 이후 시각 기준으로 스케줄만 적용, 수동/오버라이드는 날림”


이렇게 하면 사용자가 제품 성향에 맞게 선택할 수 있습니다.

6. 사용자 인터랙션 UX 관점 보완 (기능은 있지만 써먹기 좋게)

이미 백엔드 API는 꽤 잘 되어 있어서,
“프론트에서 쓰기 편한 추가 데이터/동작” 위주로 정리해볼게요.

1. /api/control/summary 응답에 다음 정도 필드 보강 추천

mode : "OFF" | "PROFILE" | "SCHEDULE" | "OVERRIDE" | "SIM"

source : "user_profile:3", "schedule:2", "override:preset:MIDNIGHT_BREEZE" 등

fan_percent : 현재 최종 PWM %

target_percent : WindSolver가 목표로 잡은 값

autoOff_remain_sec : 남은 자동 OFF 시간 (있으면)


→ 이걸 한 번에 주면, 프론트에서

“지금 왜 이렇게 돌고 있는지”

“언제 꺼질 예정인지”

“무슨 모드인지” 를 쉽게 그려줄 수 있어요.



2. override 호출 시 남은 duration을 요약해서 반환

지금은 /api/control/override/fixed / preset 호출 후
그냥 {result:"ok"} 정도만 나가는데,

내부에서 endTimeEpoch 같은 걸 잡고 있다면,

응답에 expireEpoch / remainSec 정도 넣어주면
UI에서 “강풍 15분 남음” 같은 표시 가능.

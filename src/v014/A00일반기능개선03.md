1. 부팅 & 초기화 플로우 점검

현재 SC10_init() 흐름:

1. Logger 초기화


2. LittleFS 마운트


3. Config 로드 (CL_C10_ConfigManager::loadAll(g_A10_config_root);)


4. NVS 초기화 (CL_N10_NvsManager::begin();)


5. Wi-Fi 초기화 (CL_WF10_WiFiManager::init(...))


6. PWM 초기화 (g_P10_pwm.P10_begin(...))


7. ControlManager 초기화 (CL_CT10_ControlManager::begin();)


8. MotionLogic 초기화


9. WebAPI 초기화 (CL_W10_WebAPI::begin(...))


10. AsyncWebServer 시작 + WDT



✅ 좋은 점

순서가 자연스럽다

Config → Wi-Fi → Control → Web 순으로 올라가서,
Web에서 API 호출할 때 기본 설정들이 이미 준비된 상태.


FactoryReset, NVS Flush, Watchdog까지 갖춰져 있어서
“두고 돌리는 기기”로서 기본 내구성 구조는 잘 잡혀 있음.


🔍 개선 제안

1. Config 포인터 null 방어 강화

몇 군데서 바로 이렇게 쓰고 있어요:

const ST_A10_WifiConfig&   v_wifi = *g_A10_config_root.wifi;
const ST_A10_SystemConfig& v_sys  = *g_A10_config_root.system;

그리고 routeStaticAssets() 에서도:

auto& v_web = g_A10_config_root.system->system.web;

만약 loadAll() 실패 / 일부 구조체만 null인 비정상 상황이면
→ 바로 크래시 포인트입니다.

추천: 최소한 이 정도 가드 한 번:

if (!g_A10_config_root.system || !g_A10_config_root.wifi) {
    CL_D10_Logger::log(EN_L10_LOG_ERROR, "[SC10] Config root is null. FactoryReset or fallback required.");
    // ① FactoryReset 유도 or
    // ② 안전한 디폴트 구조체로 채우기
}

routeStaticAssets() 안에서도:

if (!g_A10_config_root.system) {
    CL_D10_Logger::log(EN_L10_LOG_ERROR, "[W10] system config null. using default main page fallback only.");
    // v_web 접근 없이, pages JSON만 기준으로 라우팅
}

2. Wi-Fi / 시간 동기화 흐름

현재 구조

SC10_init() 에서:

CL_WF10_WiFiManager::init(v_wifi, v_sys, g_SC10_wifiMulti);

NTP 동기화는

부팅 시 init() 내부의 syncTimeIfNeeded()

/api/system/time/set → WF10_applyTimeConfigFromSystem() 경유로 수행



✅ 좋은 점

sync_interval_min 을 활용해서 주기적 재동기화 고려됨

WF10_applyTimeConfigFromSystem()가 시간 설정 + 즉시 sync 시도 + interval 업데이트까지 한 번에 처리 → API에서 쓰기 편함


🔍 개선 제안

1. 시간 설정 함수 위치 이동

이미 고민하셨던 것처럼, WF10_applyTimeConfigFromSystem()는
“WiFi 모듈”이라기보다 “System/TimeManager 모듈” 역할에 가깝습니다.

지금 구조도 동작에는 문제 없지만:

모듈 책임 관점에서는
T10_TimeManager 또는 S10_SystemTime 같은 쪽으로 옮기고
WF10에서는 **단순히 “NTP를 위한 연결 상태 제공자”**만 담당하게 하는 게 더 깔끔합니다.


👉 실질적인 기능 문제는 없고, 책임 분리/가독성 차원의 리팩터링 포인트 정도로만 기억해두시면 됩니다.


2. 시간 동기화 실패 시 재시도 정책

현재 syncTimeIfNeeded() / WF10_applyTimeConfigFromSystem() 모두
5~10초 동안 폴링 후 실패하면 로그만 남기고 끝입니다.

제안: s_timeSynced가 false 상태로 일정 시간(예: 10분) 이상 유지되면
→ SC10_run() 루프에서 “시간 재동기화 요청” 플래그를 한 번 더 태우는 식도 고려 가능.


지금도 큰 문제는 아니고, “네트워크 처음 붙을 때 NTP 서버 응답 느릴 경우” 정도에 대비하는 용도라 선택 사항입니다.

3. Web API / 라우팅 / 정적 자산

현재 구조 정리

REST API

/api/version, /api/state, /api/system, /api/wifi, /api/motion, /api/user_profiles...

/api/schedules, /api/windProfile, /api/control/*, /api/system/time/set 등


정적 자산

W10_Web_Static_031.cpp

/json/cfg_pages_031.json 기준

pages[], assets[], reDirect[] 로 라우팅 생성


serveStatic("/html_v2", LittleFS, "/html_v2");
→ JSON에 없는 /html_v2/** 파일 일괄 서빙


메뉴 API

/api/v1/menu : 정렬된 pages + isMain, enable 포함 반환


Upload / OTA

/upload : LittleFS 파일 등록

/update : FW OTA



✅ 좋은 점

API 모듈 구조가 잘 나뉘어 있음

Routes, Static, Upload, WS 로 잘 분리되어 읽기 좋음


정적 라우팅 구조가 확장 가능

cfg_pages_031.json 하나로 메뉴 + html + css/js + redirect 를 모두 컨트롤


serveStatic("/html_v2"... 로 이미지/잡파일 등 관리 어려운 것만 풀 라우팅 → 의도에도 맞음


🔍 개선 제안

1. s_routes_static 용량 여유

#define G_W10_PAGE_ROUTES_MAX 40

pages × (uri + path + pageAssets ×2) + assets ×2
이 조합이면 40은 금방 넘어갈 가능성 있습니다.

넘어가면 현재는 로그만 찍고 추가 라우트는 조용히 무시됨.


👉 80~120 정도로 넉넉히 올려두는 걸 추천합니다.


2. /api/system/time/set 의 응답에 현재 시간 포함

현재는:

v_res["updated"] = v_changed;
v_res["status"]  = "applied" or "no_change";

여기에 응답 편의성을 위해:

time_t now = time(nullptr);
v_res["epoch"] = (uint32_t)now;

정도만 넣어줘도,
프론트에서 “실제 반영된 시간”을 확인할 때 유용합니다.


3. WebSocket 인증

REST API는 checkApiKey()로 보호되어 있지만

WebSocket(/ws/log, /ws/state, /ws/chart, /ws/metrics) 는 현재 무제한 접근 가능


사설 네트워크 장비면 괜찮지만, 나중에 외부 포트 노출할 계획이 조금이라도 있다면,

WS URL에 ?key=... 형태로 간단한 검증이라도 추가하는 걸 추천합니다.
(복잡하게 할 필요는 없고, API 키와 동일 값 체크 정도만 해도 “아무나 보는” 문제는 줄어듦)

4. CT10 연계 / 상태 브로드캐스트 플로우

현재 플로우

SC10_run() 에서:

CL_CT10_ControlManager::tick();

auto& v_ctrl = CL_CT10_ControlManager::instance();

if (v_ctrl.consumeDirtyState()) { ... broadcastState(...) }
if (v_ctrl.consumeDirtyMetrics()) { ... broadcastMetrics(...) }
if (v_ctrl.consumeDirtyChart()) { ... broadcastChart(...) }
if (v_ctrl.consumeDirtySummary()) { ... toSummaryJson(...) }

CL_W10_WebAPI 쪽은

WebSocket 엔드포인트 등록 및

브로드캐스트 호출 유틸 (broadcastState/Metrics/Chart) 제공



✅ 좋은 점

책임 분리가 잘 됨

“무엇이 Dirty인지”는 CT10이 판단

“그걸 어떻게 보내는지”는 W10이 담당

“언제 체크할지 / 얼마나 자주 보낼지”는 SC10 메인 루프에서 컨트롤


WebSocket 접속 시 초기 스냅샷을 보내는 구조 (toJson, toMetricsJson) 도 잘 들어가 있음


🔍 개선 제안

1. 메트릭/차트 전송 주기 로깅

이미 CT10 안에서 1.5초/주기 등으로 Dirty를 관리하고 있을 텐데,
가끔 디버깅 시 “생각보다 자주 혹은 덜 나간다” 느껴질 수 있으니
→ 특정 디버그 빌드에서만
Dirty 소비 시 타임스탬프 로그를 잠깐 찍어보는 옵션 정도 고려해볼 수 있습니다.
(필수는 아님, 튜닝/디버그용)


2. 루프 내 delay(10) 영향

SC10_run() 끝에:

delay(10);

10ms면 충분히 짧고,
AsyncWebServer / WebSocket 동작엔 문제 없습니다.
다만 나중에 정밀 주기 제어(예: 1kHz PWM 피드백 루프)를 loop에 직접 넣고 싶어지면
→ delay(0) 또는 non-blocking 방식으로 바꾸는 정도 검토.


지금 구조에선 그대로 두셔도 괜찮아요.

5. 안정성 & 보안 관점의 체크리스트

a. 업로드 / OTA 보호

현재 /upload, /update 도 checkApiKey() 로 보호되고 있음 → OK

단, 업데이트 실패 시 롤백 전략은 ESP OTA 기본 메커니즘에 맡기고 있어서
“중간에 전원 나가면?” 같은 극단적인 경우는 어쩔 수 없는 구조.
(일반 ESP 프로젝트와 동일 수준)


b. FS / JSON 오류 시의 fallback

cfg_pages_031.json 이 깨져 있거나 누락된 경우:

W10_loadPagesJson() 에서 false 리턴,
→ routeStaticAssets() 가 “라우트 등록 못함” 로그만 찍고 끝.

그 뒤 serveStatic("/html_v2"... 가 있으므로,
/html_v2/... 직접 치면 열리긴 하지만,
/ , /api/v1/menu 등은 정상 동작 X.



👉 만약 이 상황을 대비하고 싶다면:

routeStaticAssets() 실패 시
최소한 / → /html_v2/P010_main_021.html 정도의 하드코딩 fallback 라우팅을 한 번 더 넣어줄 수 있음.

간단히라도 API 키 기반 보호를 넣을지 여부 한 번 검토
